# PERF-1143: Unroll Buffer Type Check in Final Frame Write

## Focus Area
The final frame write fallback at the end of the `CaptureLoop.ts` `run()` function uses `isDomStrategy` to determine how to format and encode the final buffer for stream output.

## Background Research
At the end of the `CaptureLoop` `run` function, we write the final buffer:
```typescript
    console.log("Finishing render strategy...");
    const finalBuffer = await this.pool[0].strategy.finish(this.pool[0].page);
    if (finalBuffer && finalBuffer.length > 0) {
      console.log(`Writing final buffer...`);
      if (isDomStrategy) {
        if (!stdin!.write(finalBuffer as any, "base64")) {
          await this.drainPromise;
        }
      } else {
        if (!stdin!.write(finalBuffer as any)) {
          await this.drainPromise;
        }
      }
    }
```
Although it only runs once per render, the single-worker path has already split into `if (isDomStrategy)` vs `if (!isDomStrategy)` at the highest level (PERF-988 / PERF-1130). However, the `finalBuffer` handling is currently unified at the end of the file. By moving the `isDomStrategy` check out, we might be able to simplify this logic. However, since it only runs once at the very end of the function, unrolling it provides almost zero performance benefit.

Looking at `isDomStrategy` logic in the multi-worker loop, `worker` functions also use `isDomStrategy`:
```typescript
        const isDomStrategy = !!(strategy as any).beginFrameParams;
```
If we check single worker logic:
```typescript
      const isDomStrategy = !!(strategy as any).cdpSession;
```
There's an inconsistency in how `isDomStrategy` is identified between `runWorker` (multi-worker) and single-worker. But this is not a performance issue.

Let's look for loops or redundant assignments.
In `CaptureLoop.ts`:
```typescript
              const pipelineLimit = nextFrameToWrite + maxPipelineDepth;
              let dispatches = (pipelineLimit < totalFrames ? pipelineLimit : totalFrames) - nextFrameToSubmit;
```
PERF-1142 hoisted this to a constant. However, the microbenchmark shows that hoisting it does not improve performance in Node 22 (V8 TurboFan actually optimizes the inline ternary expression better than assigning an intermediate `pipelineLimit` variable when it comes to register allocation for simple bounds checks). Since PERF-1142 was just committed and the `pipelineLimit` hoisting is slightly slower/same, reverting it isn't worth a full plan unless it's a regression.
